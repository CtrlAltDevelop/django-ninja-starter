# The example project

One project, generated by the package, with every app turned on and a feature
app of its own. It is not a snippet directory: `examples/build.py` runs the same
`create_project` the `django-ninja-starter` command runs, so what you explore
here is what the published package emits — and when the package stops emitting
it, `tests/test_example_project.py` fails.

```bash
python examples/build.py       # into examples/.build/example-api
python examples/walkthrough.py # tour every app in it, offline
```

The walkthrough builds the project itself on first run, so the second command
alone is enough.

## What gets built

`build.py` does four things, all of them things the README tells a reader to do:

1. Generates `example-api` with the packaged generator.
2. Copies `env.example` in as the project's `.env` — four login methods, four
   second factors, four social providers and all three token modes installed
   with `rotation` issuing, plus both feature apps the template ships: the
   **CMS** and **notifications**.
3. Runs the project's own `manage.py startapi notes --api-version v1` and `v2`,
   then copies `notes/` over the scaffolding it wrote.
4. Runs `migrate`, so `make run` inside the built project serves the API.

The build directory is ignored by git. Rebuild it against the current template
whenever you like:

```bash
python examples/build.py --rebuild
```

## The tour

`walkthrough.py` prints a transcript of the calls a real client would make:
sign-up and sign-in on all four methods, enrolling and using all four second
factors, the notes app across both versions, the CMS in two languages, the
notification API and its WebSocket, refresh and revoke, the social start
endpoints, the audit trail, the JWT claims and both OpenAPI documents.

It drives Django's test client in-process rather than a running server, because
the codes these flows send out are the point of the demo and only a process
holding the outbox can read them back. Routing, middleware, authentication and
the views are the same ones `runserver` uses, and the printed paths are real.

The WebSocket is driven the same way. An ASGI application is a callable taking a
scope and two channels, so the tour supplies the two queues a server would have
supplied and calls the project's own `config/sockets.py` — no uvicorn, no open
port, and the path resolved by the routing a real connection would hit.
`runserver` could not have served it in any case: Django's development server is
WSGI, which is why the generated project ships `make serve`.

Because the socket reaches the ORM on a worker thread, the tour runs against a
*shared* in-memory database (`file:walkthrough?mode=memory&cache=shared`) rather
than a plain `:memory:`, which SQLite hands out privately per connection.

It runs inside the built project as a child process — this checkout has a
`config` and an `infrastructure` package of its own, and a tour that imported
the wrong one would prove nothing.

Anything set in your shell wins, so one switch re-runs the whole thing under a
different configuration:

```bash
DJANGO_AUTH_TOKEN_MODE=sliding python examples/walkthrough.py
```

## The two feature apps that ship

`cms/` and `notifications/` are not in this directory. They come out of the
generator inside every project it writes, and the `.env` above is the whole of
what turns them on — which is the property worth seeing, so the tour reads their
settings back before it calls them.

The CMS section builds a site the way the admin would: a page with sections and
typed fields, a library footer placed on it, a menu, a draft reachable only
through a signed preview link, and the same page in Persian falling back
field by field. Then it reads all of it over the public API.

The notifications section does the HTTP half — the list, the badge, marking one
read, and another account's notification answering 404 — and then holds three
sockets open: one anonymous connection receiving a broadcast with no credential
at all, one that authenticates mid-connection and picks up its backlog, and one
that presents a token in the handshake. It also sends a bad id, because the
answer being a frame rather than a close is the part a client depends on.

## The notes app

`notes/` is the feature app the build installs: a model owned by
`settings.AUTH_USER_MODEL`, an admin, schemas, two API versions over one set of
models, and tests. Copy it into a project of your own as `src/apps/notes/` after
running `startapi notes --api-version v1`, or read it for the four things it is
there to show:

- **Ownership is a queryset filter, not a post-fetch check.** Another account's
  id is a 404, because a 403 would confirm the id exists.
- **`PATCH` is partial.** An omitted field is left alone.
- **Two versions, one model.** v1 keeps returning whole notes; v2 returns
  excerpts and adds search, because trimming a list response is a breaking
  change.
- **The tests are the ones the starter's own suite runs**, under the same
  all-apps-on settings as everything else in the project.

## Files

| Path              | What it is                                            |
| ----------------- | ----------------------------------------------------- |
| `build.py`        | Builds the example project with the packaged generator |
| `walkthrough.py`  | The end-to-end tour, run inside that project           |
